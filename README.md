# Local AES-256 ZIP

[![wakatime](https://wakatime.com/badge/user/a0b906ce-b8e7-4463-8bce-383238df6d4b/project/f2d9e7f7-e2b1-4b3d-bd11-a1149d9b6666.svg)](https://wakatime.com/badge/user/a0b906ce-b8e7-4463-8bce-383238df6d4b/project/f2d9e7f7-e2b1-4b3d-bd11-a1149d9b6666)

A static, browser-only web application for creating password-protected ZIP archives using **WinZip AES-256 (AE-2)**. Files, filenames, passwords, and generated archives are processed locally and are never intentionally transmitted by application code.

## Security properties

The ZIP layer is deliberately small and isolated in `src/zip.ts`:

- `@zip.js/zip.js` is pinned to `2.8.51`.
- `encryptionStrength: 3` is set explicitly at the writer and entry levels. In zip.js, strength `3` means AES-256.
- `zipCrypto: false` is set explicitly at the writer and entry levels. There is no fallback to traditional ZipCrypto.
- zip.js 2.8.34 writes WinZip AES extra field `0x9901` with vendor version `2` (AE-2), vendor id `AE`, and the configured strength byte.
- `tests/helpers/zip-format.ts` is an independent ZIP-header parser. The test suite checks the actual generated bytes for the encrypted flag, method `99`, AES extra field `0x9901`, AE-2 version `2`, vendor id `AE`, strength `3`, and AE-2 CRC behavior. This catches accidental plaintext or ZipCrypto output even if application configuration changes.
- The app imports zip.js's `lib/zip-core-native.js` entry point and disables web workers. That avoids worker and WASM asset loading at runtime while retaining the package's bundled JavaScript compression fallback.

## Zero-upload design

There are no application API endpoints, authentication services, databases, Cloudflare Workers, Pages Functions, analytics, telemetry, error-reporting SaaS, external fonts, CDN scripts, or dynamically loaded third-party code.

Defense in depth:

1. The application itself contains no network calls for file processing.
2. In production builds, `src/network-guard.ts` replaces `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, and `navigator.sendBeacon` with blocked implementations at runtime. The guard is intentionally not installed by the Vite development build so local HMR can work.
3. The production CSP uses `connect-src 'none'`, so browser connection APIs are denied by policy too.
4. `worker-src 'none'` is compatible because zip.js web workers are explicitly disabled.
5. All runtime dependencies are bundled by Vite into local static assets. Vite's module-preload polyfill is explicitly disabled so it cannot add a hidden runtime `fetch` path.
6. Downloads use a local `Blob` object URL. The previous URL is revoked when replaced and on page unload.

The HTTP GET requests needed to initially load the site's own HTML/JS/CSS from the static host are, of course, network traffic. The zero-upload claim concerns user files, filenames, passwords, and generated archive data: application code never sends those values to a server.

## Password behavior

The password and confirmation must be non-empty and match. A strong-password generator uses `crypto.getRandomValues()` with rejection sampling; it does not use `Math.random()`.

The **Remember password on this device** option stores the password in `localStorage`. This is convenience storage, not a secure vault: any JavaScript executing with access to the same origin can read it. The UI never describes localStorage as encrypted or equivalent to Bitwarden, Keychain, or another password manager. Users who need strong password handling should generate/store the password in a dedicated password manager such as Bitwarden instead.

The password is never intentionally placed in a URL, query string, fragment, filename, console log, analytics event, IndexedDB entry, or network request.

## What this protects against — and what it does not

AES-256 encryption protects ZIP contents from someone who has the archive but does not know the password. A publicly downloadable encrypted ZIP can still be attacked offline, so password entropy matters greatly; use a long, unique, randomly generated password.

WinZip AES encrypts entry data, but standard ZIP filenames and some metadata remain visible in the archive directory. Do not assume the archive hides filenames merely because file contents are encrypted.

This design does **not** make the hosting site inherently trustworthy. JavaScript delivered by the site executes before encryption and could access files and passwords if the deployed application were malicious or compromised. Review the source, pin deployments, and protect the hosting account/supply chain accordingly.

`localStorage` is convenience storage and can be read by same-origin JavaScript. It is not an encrypted secret store.

Public hosting of the resulting ciphertext is compatible with this architecture because plaintext does not need to be uploaded to create the encrypted archive. Whether publishing a particular encrypted archive is appropriate is still a separate operational decision.

This project intentionally avoids absolute claims such as “zero knowledge” or “impossible to break.”

## Large files and directories

Files are handed to zip.js as `BlobReader` instances and processed sequentially rather than reading every selected file into one giant `ArrayBuffer`. Directory paths are preserved when supplied by `webkitdirectory` or drag/drop directory entries supported by the browser. Empty directories are not materialized because the UI tracks files rather than standalone directory entries.

The final archive is represented as a browser `Blob` so it can be downloaded with an object URL. That means the browser still needs enough practical storage/memory capacity for the output archive and library buffers. Limits vary by browser, OS, available memory, and storage pressure. Cancellation uses `AbortController` and zip.js's `signal` option.

## Browser support

Use a current browser with Web Crypto, Web Streams, `Blob`, and modern file APIs. Folder selection is best supported in Chromium-family browsers through `webkitdirectory`; drag/drop directory traversal also depends on browser support. Multiple ordinary files work wherever modern file inputs are supported.

## Development

Prerequisites: Bun 1.3.14 for the `bun:test` suite, or a Vite-supported Node.js release (`20.19+` or `22.12+`) for build/preview. Dependency versions in `package.json` are exact rather than ranges.

```bash
bun install
bun run dev
```

Quality checks:

```bash
bun run typecheck
bun run lint
bun test
bun run build
bun run audit:dist
```

Or run everything:

```bash
bun run check
```

The tests use `bun:test` and the requested `it("should …")` convention. If `7zz` or `7z` is installed, the suite also runs `tests/interop-7zip.test.ts`, which verifies that an independently implemented archiver recognizes the generated ZIP as AES-256 and can extract it. That test is skipped when no 7-Zip executable is present.

## Cloudflare Pages deployment (static only)

This repository has no `/functions` directory and no server-side code.

For Cloudflare Pages:

- Framework preset: **Vite** (or no preset with the same settings)
- Build command: `npm run build` or `bun run build`
- Build output directory: `dist`
- Root directory: repository root
- No Workers bindings, Pages Functions, databases, auth, environment secrets, or API endpoints are required.

`public/_headers` is copied by Vite to `dist/_headers`. The CSP intentionally has **no** `unsafe-inline` or `unsafe-eval` exception. `connect-src 'none'` blocks application network connections, and `worker-src 'none'` is compatible with `useWebWorkers: false`.

The headers file also sets `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, a restrictive `Permissions-Policy`, `Cross-Origin-Opener-Policy`, and `Cross-Origin-Resource-Policy`.

**Hosting invariant:** keep Cloudflare Web Analytics, Zaraz, and any other automatic script-injection/telemetry feature disabled for this Pages project and its custom domain. Those optional platform features can add JavaScript that is not part of this audited static bundle, which would expand the same-origin trust boundary and violate this project's zero-upload/no-telemetry requirements. Treat the deployed HTML and DevTools Network panel as part of the release audit; do not rely on CSP as a substitute for disabling injected scripts.

## Independent AES-256 verification

### Automated byte-level test

Run:

```bash
bun test tests/zip.test.ts
```

The test generates an archive, parses the ZIP structures independently of zip.js, and asserts:

- general-purpose encrypted bit is set;
- compression method in the ZIP header is `99` (WinZip AES marker);
- extra field id is `0x9901`;
- vendor version is `2` (AE-2);
- vendor id is `AE`;
- strength is `3` (AES-256);
- AE-2 CRC field is zero;
- an incorrect password fails extraction.

Traditional ZipCrypto does not use the method-99 + `0x9901` WinZip AES metadata combination, and plaintext ZIPs do not set the encrypted flag.

### 7-Zip / macOS interoperability

7-Zip publishes a native macOS console build. With `7zz` or `7z` on `PATH`, `bun test` automatically runs the independent interoperability test. You can also create a small archive in the browser with a disposable test password and inspect it manually:

```bash
7zz l -slt encrypted.zip
```

For encrypted entries, inspect the method/encryption information and confirm it reports AES-256 rather than ZipCrypto. Then test extraction. Prefer interactive password entry or a disposable test password instead of placing a real secret directly on a shell command line, where it may be exposed through shell history or process inspection.

A macOS archive utility must explicitly support WinZip AES to open the archive. 7-Zip is the reference check for this project; other compatible macOS tools can be used as a second interoperability check. Apple's built-in Archive Utility should not be treated as the compatibility reference for WinZip AES archives.

## Inspect the built site for unintended network behavior

1. Build with `bun run build` and run `bun run audit:dist`.
2. Serve `dist/` with any basic static server, for example:

   ```bash
   python3 -m http.server 4173 --directory dist
   ```

3. Open `http://localhost:4173` in a browser.
4. In DevTools → Network, let the initial local HTML/JS/CSS finish loading, then clear the log.
5. Select files, enter a password, create an archive, and download it.
6. There should be **no new application network requests** during file selection, encryption, ZIP generation, or download. The download itself uses a `blob:` URL.
7. In DevTools → Application/Storage, verify that the only password persistence is the documented `localStorage` key when “Remember password” is enabled, and that clearing it removes the key.

A generic local static server does not apply Cloudflare's `_headers` file; the app should still function there. Verify the actual CSP/headers after deploying to Cloudflare Pages as a separate deployment check.

## Project structure

```text

  files.ts          file/directory selection and relative paths
  main.ts           UI state and event handling
  network-guard.ts  defense-in-depth blocking of network primitives
  password.ts       validation, generation, localStorage persistence
  zip.ts            isolated, auditable WinZip AES-256 implementation
  types.ts          shared strong types
  style.css         local-only UI styling

tests/
  helpers/zip-format.ts     independent ZIP/AES metadata parser
  files.test.ts             safe path and de-duplication tests
  password.test.ts          validation, persistence, RNG tests
  zip.test.ts               archive generation, AES-256, decrypt/cancel tests
  interop-7zip.test.ts      optional independent 7-Zip interoperability test
  network.test.ts           zero-upload runtime/CSP tests

public/_headers      Cloudflare Pages security headers
scripts/audit-dist.mjs  post-build static-site audit
```
